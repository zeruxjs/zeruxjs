The zeruxjs package

Install the framework and choose its public entry points intentionally.

Responsibilities#

The main package coordinates configuration, application module discovery, HTTP dispatch, services, workers and builds. Ecosystem packages provide focused functionality. Installing the main package does not automatically turn every optional package into a configured service.

Installation and application commands#

sh
npm install zeruxjs@0.0.4 @zeruxjs/typescript@0.0.4
npx zerux dev
npx zerux build
npx zerux start

Run commands inside your application directory. Configure infrastructure and domains before deployment. Use the implemented SSR generator, manual installation guide or tutorial.

Root exports#

Import public types and helpers from zeruxjs: ZeruxConfig, ZeruxPluginApi, ZeruxRequestContext, startup/thread-worker helpers, HttpError, logger/Logger, navigation, cache/stream responses, protocol factories, metrics, Fetch bridge helpers, service lifecycle functions, application build helpers and template variables. Prefer the focused subpath when it makes a runtime dependency explicit.

Cache and service ownership#

zeruxjs/cache reexports active-manager convenience methods from the cache package. For explicit multi-application/generation ownership, use the manager supplied through api.service or context.services.get instead of assuming a process-active facade is request-local. Construct standalone managers when the caller owns shutdown.

Build contract and boundaries#

The server compiler stages application modules and public assets; it does not promise a generic static export, a typecheck or arbitrary external worker-file compilation. The production resolver uses a valid build manifest when present and can fall back to source configuration when absent. Verify your artifact and built path explicitly.

React/Vue state adapters, standalone Zyro rendering and host-configured CMS/generator packages have separate contracts. Use the capability map and task guides rather than interpreting a roadmap statement as an implemented framework integration.

TypeScript configuration and service access#

Use ZeruxConfig for application setup and narrower nested types for each configured service. The configuration handbook maps every declared setting to its actual consumer and startup policy. A root extension key is not automatic service initialization.

ts
import type { ZeruxConfig, ZeruxRequestContext, ZeruxPluginApi } from 'zeruxjs';
const config = { type: 'fix', cache: { connector: 'memory', prefix: 'application' } } satisfies ZeruxConfig;
type Context = ZeruxRequestContext;
type Plugin = (api: ZeruxPluginApi) => void;

Service managers are generation-owned and can be disabled/degraded. Use their concrete factory return type for typed lookup and check availability; do not turn optional access into an unchecked non-null assertion. The TypeScript guide explains strict NodeNext configuration, unknown-data validation and virtual-import boundaries.

Production verification path#

Create one route, run development, build, then start the compiled application. Verify its host policy and configured infrastructure before adding more services. Read the production checklist, service lifecycle and configuration entry point. Source README roadmap statements do not replace these implemented contracts.

Coordinated subject privacy operations#

The optional Node-only zeruxjs/privacy entry exposes a headless host-authorized coordinator. Explicit participants declare find/export/erase coverage and exclusions; no subject identity, object ownership or remote erasure capability is inferred from an email, service name or report source. The package README lists actual service contracts and missing host mappings.

Jobs require verified subject linkage, per-operation authorization, preview pages, expiring approval evidence and a durable private CAS/checkpoint journal. Resume rechecks authorization and processes one bounded participant page. Local page receipts must be durable/idempotent with effects; uncertain outcomes recover receipts rather than automatically repeating deletion. Retained holds, inaccessible providers and backups remain visible as partial coverage. No cross-store transaction or legal compliance guarantee is implied.

Private expiring JSONL exports use approved projections and bounded streams, with per-chunk authorization/expiry checks and no public URLs. Host routes still own CSRF/authentication, private attachment headers and disconnect cleanup. The public examples/privacy.mjs demonstrates explicit injection. Synthetic fixtures verify checkpoint recovery and partial completion; no real user-data deletion was run.

Local integration hosts#

server.watchIgnoredPaths accepts up to 64 project-relative directories, such as [".workspace"], and is omitted from public config. ZeruxJS forwards these exclusions and its runtime directory to zhost before source scanning. This is watch policy, not file authorization.

Trusted plugins can obtain the optional borrowed host bus through api.lifecycleHooks?.(). Register observers only when a host supplied the bus and remove their tokens with api.onDispose; getConfig() deliberately does not expose the private lifecycle authority. No bus is created implicitly.

Prebundled browser assets may use local {exports:{}} wrapper data. That does not permit free exports, module, require or globalThis.exports in client graphs.

Full package README

zeruxjs#

ZeruxJS is a Node.js application framework with file-based routing, middleware, plugin registration, runtime services, startup workers and worker-thread pools. Its hosting and protocol integration uses zhost; shared commands, file watching and development tools use zclivo, zlook and zforge.

Getting started#

Use the repository's installation guide and tutorial, or inspect apps/zeruxjs-app for a development example. zclivo create provides a minimal starter. The separate create-zerux-js CLI now supplies validated HTML-only SSR starters.

React/Vue observable adapters are available as separate packages. Opt-in static renderer factories are described below; the state adapters do not install UI runtimes or a general SSR hydration pipeline. Configure authentication, trusted proxies and service credentials explicitly for each application.

Runtime Workers and Thread Workers#

Startup workers run after ZeruxJS finishes bootstrapping the runtime and before the HTTP server starts accepting requests. They are useful for background queues, schedulers, cache warmups, shared workers, and other services that must be ready before routes run.

Thread workers use Node.js worker_threads for CPU-heavy or isolated tasks. Set default thread limits in zerux.config.ts:

ts
import type { ZeruxConfig } from "zeruxjs";

const zeruxConfig: ZeruxConfig = {
  worker: {
    minThreads: 1,
    maxThreads: 4
  }
};

export default zeruxConfig;

Register workers from a plugin or app entry file:

ts
import { defineThreadWorker, defineWorker, type ZeruxPluginApi } from "zeruxjs";

export default (api: ZeruxPluginApi) => {
  api.addWorker("queue", defineWorker("queue", async ({ logger, state, env }) => {
    const queueUrl = env.QUEUE_URL;
    if (!queueUrl) {
      throw new Error("QUEUE_URL is required to start the queue worker.");
    }

    state.set("queue", { startedAt: new Date().toISOString() });
    logger.info("Queue worker started");

    return async () => {
      logger.info("Queue worker stopped");
    };
  }));

  api.addThreadWorker("math", defineThreadWorker("math", "workers/math.ts", {
    minThreads: 1,
    maxThreads: 2
  }));
};

Thread worker modules export a function:

ts
export default function mathWorker(payload: { value: number }) {
  return {
    squared: payload.value * payload.value
  };
}

Use a thread worker from a route, middleware, or startup worker:

ts
const math = context.runtime.asPluginApi().getThreadWorker("math");
const result = await math?.run({ value: 12 });

Worker helpers:

  • defineWorker(name, handler): creates a typed worker object.
  • registerWorker(api, name, worker): small helper around api.addWorker.
  • api.addWorker(name, worker): registers a worker directly.
  • api.removeWorker(name): removes a registered worker before startup.
  • api.getWorker(name) and api.getWorkers(): inspect registered workers.
  • defineThreadWorker(name, script, options): creates a thread worker pool definition.
  • registerThreadWorker(api, name, worker): small helper around api.addThreadWorker.
  • api.addThreadWorker(name, worker): registers a Node.js worker thread pool.
  • api.getThreadWorker(name) and api.getThreadWorkers(): inspect and run thread pools.

The startup worker handler receives { runtime, mode, config, structure, logger, env, state }. Return a cleanup function when the worker owns intervals, sockets, queues, or other resources. In dev mode cleanup runs before the runtime is rebuilt, then the new worker set starts again. Thread pools are also stopped before dev reloads and restarted with the new runtime.

Navigation#

Use zeruxjs/navigation when a route handler or middleware needs to return an HTTP redirect:

ts
import { redirect, RedirectType } from "zeruxjs/navigation";

export const GET = () => {
  return redirect("/dashboard", RedirectType.Temporary);
};

RedirectType includes Temporary (307), Permanent (308), Found (302), and SeeOther (303).

Multisite Routing#

Enable request-scoped multisite routing in zerux.config.ts:

ts
import type { ZeruxConfig } from "zeruxjs";

const zeruxConfig: ZeruxConfig = {
  multisite: true
};

export default zeruxConfig;

Register host and path mappings from middleware:

ts
export default async (context, next) => {
  context.multisiteRegister("*", "main");
  context.multisiteRegister("meow.com", "main");
  context.multisiteRegister("meow.com/apple/cat", "cat");
  context.multisiteRegister("meow.com/apple", "apple");

  await next();
};

Use * as the host to match any incoming host for that registration, such as local IPs, localhost, or temporary domains. Exact hosts still take priority over wildcard hosts when the path specificity is the same. Zerux sorts registrations by path depth before matching, so meow.com/apple/cat is checked before meow.com/apple. A match rewrites the internal route pathname to the selected root app folder segment. For example, meow.com/apple/api/health with folder apple routes through app/{apple}/api/health/route.ts.

When multisite is enabled and middleware registers mappings, requests that do not match any mapping are not allowed to fall through into root dynamic routes. This keeps an explicit mapping such as meow.com from accidentally serving an unrelated host like cat.com/something.

Protocol registration, cache control, streams and load metrics#

ZeruxJS now integrates the ZHOST protocol gateway without importing ZHOST's CLI/dev server. In your application's entry module or plugin registration function:

ts
import { cached, stream, type ZeruxPluginApi } from 'zeruxjs';

export default function register(api: ZeruxPluginApi) {
  const protocols = api.protocols();
  protocols.rpc('math.add', params => (params as {a:number,b:number}).a + (params as {a:number,b:number}).b);
  protocols.tool('echo', 'Returns a message', {type:'object',properties:{text:{type:'string'}}}, ({text}) => text);
  protocols.connect('Messages', 'Ping', input => input);
  protocols.trpc('health.ping', () => ({ ok: true }));
  // Publish to connected SSE clients at /events: protocols.publish('update', { status: 'ready' });

  api.addRoute({ pattern: '/catalog', method: 'GET', handler: () =>
    cached({ products: [] }, { visibility: 'public', maxAge: 30, etag: true, vary: ['Accept-Language'] })
  });
  api.addRoute({ pattern: '/export', method: 'GET', handler: () =>
    stream((async function* () { yield 'first\n'; yield 'second\n'; })(),
      { contentType: 'text/plain', maxBytes: 1024 * 1024 })
  });
  api.addRoute({ pattern: '/upload', method: 'POST', meta: { streamBody: true },
    handler: async (ctx) => {
      let bytes = 0;
      for await (const part of ctx.requestStream) bytes += part.length;
      return { bytes };
    }
  });
  // Read metrics internally: api.getLoadStatus(30_000).
  // Expose them only behind your own authorization middleware.
}

/rpc, /mcp, /events, /trpc/<name>, and registered Connect endpoints are routed through the gateway before file routes or the normal 1 MiB buffered-body parser. They are local-only by default, and requests containing proxy forwarding headers are rejected unless protocols.authorize explicitly authorizes them. For deployments behind ZHOST/Nginx, configure authentication and trusted proxy controls yourself (do not trust X-Forwarded-* blindly). Limit protocols.allowedOrigins for cross-origin browser clients. MCP provides tools/resources and JSON transport subset, not the complete MCP transport surface.

cached(payload, policy) sets HTTP cache headers and optionally a content SHA-256 ETag. Cache-Control: public is an explicit decision: never use it for user-specific responses. ctx.setCache(policy) allows routes to manage response headers directly. stream(...) streams with backpressure, client-disconnect cancellation, byte ceilings and no-store, no-transform; for SSE use api.protocols().publish with the built-in replay-capable /events endpoint.

api.getLoadStatus(windowMs) and runtime.getLoadStatus(windowMs) expose bounded in-memory request counts, 1xx–5xx status families, HTTP versions, concurrency and latency. Nothing is publicly served automatically.

Fetch handlers and content integration#

ts
import { registerFetchRoutes } from 'zeruxjs/fetch-route';
import { createSearchHandler } from '@zeruxjs/search/http';
import { createCrawlerRoutes } from '@zeruxjs/seo/fetch';

export default (api) => {
  registerFetchRoutes(api, [
    { pattern: '/search', handler: createSearchHandler({ index: searchIndex }) },
    ...createCrawlerRoutes({ origin: 'https://example.com', entries: () => sitemapEntries })
  ]);
};

Fetch-compatible handlers are registered with the existing plugin API. The adapter streams request/response bodies without mandatory buffering, preserves HTTP statuses and safe end-to-end response headers, and propagates disconnect cancellation. This adapter does not automatically authorize new routes; configure middleware, visibility and allowed domains. Use registerFetchRoutes after loading the endpoint packages, or createFetchRoute to wrap an individual handler.

Development reload behavior#

Development rebuilds now stage new handlers and startup workers before switching the running HTTP handler. If the new application fails to build or start, the last successfully activated runtime stays available. dev.json includes the latest reload state and error message for diagnostics. Runtime manifests and snapshots use atomic private writes with a 4 MiB serialized-output limit. Development snapshots are fresh JSON objects on startup; prior malformed or oversized regular snapshots are replaced without reading or carrying their contents into a new generation. Workers are rolled back after partial startup failures and thread-pool tasks are rejected during shutdown.

Application build and runtime-managed services#

zerux build stages compiled TypeScript/JavaScript routes, handlers, plugins and public assets under .zerux/build. On successful completion, zerux start uses the build manifest and compiled folders; zerux dev continues to use the working sources. A failed build leaves the last good build untouched. Build output is restricted to this project and refuses symbolic links. Run a separate typecheck and install dependencies before production use.

Optional config.files, config.analytics and config.email configure generation-scoped managers after database and cache initialization. Use api.service('files'), api.service('email') and api.service('analytics') inside application plugins, or context.services.get('files') in request handlers. Manager resources close in reverse initialization order after requests from the prior generation finish. Analytics remains best-effort and email tracking remains opt-in per send.

Accessible frontend progressive enhancement#

zeruxjs/accessibility exposes bindAccessibleTabs(tabList) and prefersReducedMotion(). It is safe to import on the server (DOM globals are only read inside browser-only functions). For tabs, author actual buttons under role="tablist", give each a unique ID and aria-controls pointing to a role="tabpanel" element whose aria-labelledby points back. The binder enforces matching references, disabled tabs, roving tab index, focus and arrow/Home/End keyboard operation; call destroy() on route unmount. Orientation and RTL handling can be supplied explicitly. It never overwrites arbitrary HTML or dynamically generates IDs.

A browser fixture (under tests/browser/) covers bridge snapshot projection, explicit subscription teardown, keyboard focus, ARIA panel selection and reduced-motion styles. Run npm run test:frontend; opt into live Chromium checks with npm run test:frontend:browser when a functioning browser is installed. Standalone ZyroJS and Zuixs have separate test suites.

Project generator#

create-zerux-js generates private ZyroJS (default), React or Vue HTML-only SSR projects through the shared zclivo engine, with explicit flags/dry-run and no automatic install/start. Browser hydration and registry/source-version qualification remain separate; see its README.

Validated configuration and custom services#

resolveApplicationConfig({ defaults, file, environment, overrides }) merges in that order: later defined values win, plain objects merge recursively, and arrays replace. loadConfig(rootDir, mode, layers) chooses the first existing .ts, .js, .mjs, .cjs configuration file; CLI port overrides are applied before validation. Runtime defaults then fill omitted values. Environment layers are explicit typed values, not automatic coercion of process.env. The existing env loader preserves process values and uses first-defined values across its ordered env files.

Loading, building and service startup validate framework-owned shapes before calling connector factories. Unknown root/core service keys and unregistered services namespaces fail. Migrate ad hoc root settings into a registered namespace, or into publicSettings only when intentionally public. Invalid enabled report/dashboard authorization now fails preflight instead of waiting for optional startup degradation. Provider-specific option semantics remain the owning package's responsibility. Configuration modules, schemas and service factories are trusted executable code; schemas should be pure and may run more than once.

ts
import { defineService, createApplicationLifecycle } from 'zeruxjs';
import { object, string } from '@zeruxjs/validator/schemas';

const greeting = defineService({
  name: 'custom:greeting', namespace: 'greeting',
  schema: object({ label: string() }),
  reloadable: ['label'], publicFields: ['label'],
  start({ settings, signal, onDispose }) {
    // Register cleanup immediately after acquiring any resource.
    onDispose(() => { /* release this instance's resources */ });
    return { value: { label: settings.label, signal } };
  }
});
const app = await createApplicationLifecycle({
  rootDir: process.cwd(),
  config: { serviceDefinitions: [greeting],
    services: { greeting: { settings: { label: 'Hello' } } } }
});
try {
  console.log(app.runtime().serviceScope.get('custom:greeting'));
} finally {
  await app.close();
}

Install the optional schema package explicitly when using this example. Any compatible Standard Schema v1 object can be supplied; schema types remain owned by its package. Definitions are explicitly registered before runtime plugins load; there is no package discovery. dependencies names built-ins or custom:* services; cycles and missing declarations fail before initialization. Factories can access only declared dependencies through get. Configured namespaces default to enabled; absent namespaces are disabled. required defaults to true; false records degraded status on failure. Dependencies must be ready. Settings must validate to a bounded JSON object; private clients, credentials and callbacks belong in privateOptions.

publicFields selects JSON settings for browser manifests. publicSettings is an explicit application-owned JSON projection. Credentials, private options, callbacks and worker metadata are excluded; sensitive key names are rejected in public projections. Hosts must never deliberately publish secrets under innocent field names. Raw causes are available internally through scope errors() or thrown errors; public reload status uses generic diagnostics. The legacy redactManifestConfig helper remains available internally for compatibility, but runtime manifests use the explicit projection.

Factories return { value, dispose?, routes? }; absent dispose, a value's close() is used. onDispose callbacks run in reverse registration order after the instance disposer, including failed startup, and its signal is aborted first. Return cleanup or register it immediately: arbitrary promises cannot be forcibly cancelled. Route registration retains the existing overlap and authorization boundaries. Custom services initialize sequentially in dependency order (maximum 64) and close before their dependencies. Optional failures retain internal causes and do not grant dependent services access to unavailable instances.

createApplicationLifecycle owns handlers and service generations; it does not bind a server, start worker entrypoints, or restart applications. Route hosts through handle, and call close to drain requests and release services. reload(config) validates and stages a complete replacement before activation; failed preparation leaves the old generation usable. Only explicitly listed top-level custom settings fields are reloadable. Built-in options, private options, enabled state and executable definitions require an explicit manual restart (RestartRequiredError.fields). Reuse the same definition objects across programmatic reloads; newly evaluated executable definitions are conservatively restart-required. The CLI applies the same checks during development rebuilds. Database/cache global compatibility APIs publish at activation; staged managers must expose their non-publishing create*Manager factory. Prefer scoped services over process-global clients, especially with concurrent applications.

Request correlation, API errors and optional tracing#

Every runtime handler gets server-generated request/trace/span IDs and application/generation correlation through getRequestCorrelation(). Managed application lifecycles and CLI reloads keep the application ID stable and generate a new generation ID. IDs are bounded opaque strings, never authorization, tenant identity or deduplication keys. Incoming x-request-id is ignored. trustTraceParent: true explicitly accepts only valid version-00 traceparent parents with nonzero IDs; other versions/malformed/duplicate values start a new trace. Local sampling is independent of caller flags. No baggage, tracestate, URLs, request bodies, headers, cookies or tenant attributes are exported. This is a limited W3C Trace Context interface, not full OpenTelemetry compatibility.

ts
import { createApplicationLifecycle, getRequestCorrelation, ApplicationError } from 'zeruxjs';

const app = await createApplicationLifecycle({
  rootDir: process.cwd(),
  config: { observability: {
    applicationId: 'shop', sampleRate: 0.1, maxQueue: 128,
    exportTimeoutMs: 1000, shutdownTimeoutMs: 2000,
    createAdapter: () => ({
      // Supply an explicitly configured exporter here. This example stays local.
      export(span, signal) { if (!signal.aborted) console.log(span); },
      shutdown(signal) { /* release this generation's exporter resources */ }
    })
  } }
});
app.runtime().asPluginApi().addRoute({
  pattern: '/example',
  handler() {
    const correlation = getRequestCorrelation();
    if (!correlation) throw new ApplicationError(503);
    return { requestId: correlation.requestId };
  }
});
// Your host calls app.handle(req, res). This API never binds a port.
await app.close();

Tracing is inert without an injected adapter. Prefer createAdapter for reloadable hosts: each runtime owns one new adapter, calls optional start/end once for each admitted sampled span, and shuts it down on disposal. A direct adapter is generation-owned; managed reload rejects it with restart-required diagnostics. Use createAdapter to reload safely. Factory/start/end hooks are trusted synchronous code and must not block; exporter/shutdown promises receive cancellation signals. Exporter errors never change HTTP results. Only one export is in flight, with at most maxQueue pending/in-flight exports and maxQueue active spans (default 128; maximum 4096 each). Saturation drops telemetry, not requests. Response finish/close owns completion, including streamed responses; errors/disconnects cannot end a span twice. Exporters ignoring abort stall that generation's queue instead of creating more in-flight work. Shutdown aborts export, discards queued records, ends active spans, calls shutdown and returns by its deadline; it cannot force arbitrary promises to stop. getTelemetryStatus() reports counts, drops, failures and export timeouts without payloads. Export deadlines default to 5 seconds; budgets accept 1–60000 ms.

Zhost's existing proxy telemetry owns its response counters; the application observer owns application spans only. Do not wrap app.handle a second time. A separately instrumented proxy must create its own proxy span and explicitly propagate its span ID as the application's parent. Existing zhost forwards ordinary trace headers but does not create tracing spans or grant trust to caller headers. No host telemetry exporter is enabled automatically.

For framework-generated API errors, send an Accept header preferring application/json (or application/problem+json), or set file-route meta.api = true. Explicit JSON preference wins ties with HTML; missing/wildcard Accept preserves legacy shape. JSON responses use application/json and this envelope:

{"error":{"code":"VALIDATION_FAILED","message":"Validation failed","requestId":"server-generated-id"}}

Explicit modules, controllers and providers#

zeruxjs/modules (also exported from zeruxjs) adds an opt-in registration layer over the existing plugin routes. It requires no decorators, reflection or package scanning. Register once from an application entry/plugin function; do not retain its container across runtime generations. The existing file router, middleware, service endpoints and request lifecycle hooks remain authoritative.

ts
import type { ZeruxPluginApi } from 'zeruxjs';
import { createProviderToken, defineProvider, defineController, registerModule }
  from 'zeruxjs/modules';
import { object, string } from '@zeruxjs/validator/schemas';

const Greeting = createProviderToken<{ hello(name: string): string }>('Greeting');
export default async function register(api: ZeruxPluginApi) {
  await registerModule(api, {
    name: 'greetings',
    providers: [defineProvider({ token: Greeting, scope: 'request', dependencies: [],
      create: () => ({ hello: (name: string) => `Hello ${name}` }) })],
    controllers: [defineController({ path: '/greeting', method: 'POST',
      schema: object({ name: string() }),
      async handle(input, _context, providers) {
        return { message: (await providers.get(Greeting)).hello(input.name) };
      } })],
  });
}

Install the optional validator package explicitly for this example. schema is a Standard Schema v1 input pipe; validator transformations determine the handler's output type through defineController. No schema/auth implementation or public types move into the framework. Guards use the application's existing auth/session verification and authorization policy; a client-supplied user/tenant object is not verified identity. For cookie-authenticated writes retain configured origin/CSRF and rate-limit checks in the HTTP boundary. The example is a public greeting, not an authenticated enrollment or account operation.

Provider tokens have object identity, a typed value and a bounded diagnostic name. defineProvider infers the factory's declared dependency tuple. Dependencies must be registered in the same module; no hidden global service locator is introduced. Use a factory closure over an explicitly acquired api.service(...) for a borrowed framework service; its owner still controls disposal. Missing dependencies, cycles and singleton-to-request/transient captures reject before constructors run. Cycle errors carry the bounded token-name chain in ModuleError.code.

Scopes are singleton (one per module registration/generation), request (one per matched invocation) and transient (one per resolution). Concurrent singleton or request resolution shares its in-flight construction. Providers are lazy unless a singleton declares eager: true. Factories receive { signal, request?, onDispose }; singleton factories never receive a request. Register partial-resource cleanup immediately with onDispose; throwing construction runs those callbacks in reverse order. Successful construction retains dispose(value) and callbacks until scope teardown. Dispose dependents before dependencies, including transient instances; cleanup errors are aggregated without skipping remaining disposers.

The actual request sequence is existing request hooks/body parsing/global middleware, route resolution, existing route middleware, module guards in order, schema validation, module middleware, then controller. Module guards must return exactly true. Neither guards nor schema pipes receive a provider resolver, so a denial/invalid input cannot instantiate a privileged controller provider. The handler gets validated/transformed input; context.body remains the original parsed body. Middleware must call/await next at most once; a started downstream continuation is also awaited before returning. Existing hook phase ordering and response mutation rules are unchanged.

An optional controller filter(error, context) handles guard/pipe/middleware/handler errors. It may return a normal handler result, explicitly write/end a native response, or throw an existing ApplicationError for the framework's sanitized envelope. Setting res.statusCode alone does not change the framework's normal result status. Unhandled module guard/input errors become fixed 403/400 envelopes; internal causes, input values and dependency errors stay private. Disposal failures are reported internally, not passed to a response filter after headers commit.

Request providers reuse the real lifecycle cancellation signal and remain alive until both handler settlement and response completion/disconnect. Streamed results retain their providers through their last byte. Escaped resolvers reject after scope closure. Generation cleanup aborts/drains owned request scopes, then releases singletons before framework services. api.onDispose(cleanup) also supports explicit plugin-owned generation cleanup on normal close and failed preparation; returned plugin values are not automatically treated as disposers. Factories/handlers must cooperate with cancellation: shutdown waits for their actual settlement and never claims to forcibly stop arbitrary promises.

Registration supports canonical static paths only (no duplicate/trailing slashes), explicit HTTP methods, 128 providers/controllers per module, 32 dependencies, guards/middleware and construction disposers, 256 acquisitions per scope, and 128 plugin disposers per generation. api.hasRoute(path, method) checks an exact existing match. Module registration rejects existing same-path/method routes, rolls back its own additions on failure, and startup detects later-discovered file collisions. Reserved service/public endpoint collision checks remain intact; dynamic file routes retain the router's existing specificity ordering. An explicit module close() is idempotent and leaves its registered routes unavailable (503) until that generation is replaced. Provider values/factories never enter browser manifests. This is a small server module layer, not NestJS or browser hook parity.

Multiple service endpoints and service calls#

zeruxjs/service-endpoints (also exported from the root) provides explicit endpoint groups over zhost/protocols. No listeners start on import or registration. Every endpoint requires a name, numeric-IP bind, full message/concurrency/deadline limits and an authorization callback. HTTP endpoints own a distinct ProtocolGateway; WebSocket endpoints own a path, origin allowlist and message handler. No transport implementation moves into the framework and native gRPC registration is not added.

ts
import type { ZeruxPluginApi } from 'zeruxjs';
import { registerServiceEndpoints } from 'zeruxjs/service-endpoints';
import { createProtocolGateway, type TransportAuthorization } from 'zhost/protocols';

export function registerEndpoints(api: ZeruxPluginApi, authorize: TransportAuthorization) {
  const gateway = createProtocolGateway({ authorize: () => true });
  gateway.connect.register('app.Status', 'Read', (_input, context) => {
    context.signal?.throwIfAborted();
    return { ready: true };
  });
  return registerServiceEndpoints(api, [{
    name: 'status', transport: 'http', gateway, authorize,
    bind: { host: '127.0.0.1', port: 0 },
    limits: { maxMessageBytes: 65536, maxConcurrent: 16, timeoutMs: 5000 },
  }]);
}

Call this from an explicit entry/plugin with real host authentication. The returned handle has start, close, health and address(name). CLI startup workers start the group and return its teardown; generation onDispose is a second idempotent ownership boundary, including failed preparation. Programmatic application owners must explicitly call start() or run their startup workers: creating an application lifecycle does not implicitly bind ports. Register at most 32 endpoints in one group; { name } optionally selects its worker name. Existing worker-name, endpoint-name, fixed-port, duplicate-gateway and gateway-path conflicts reject. Port zero supports independent disposable listeners. HTTP paths remain the gateway's real registered RPC/Connect/MCP/SSE paths; WebSocket paths are configured independently. This is not an arbitrary HTTP-router remounting or universal RPC abstraction.

Group startup and rollback use zhost's real adapter registry: a failed listener closes previously acquired listeners in reverse order. Close stops admission, signals handlers, closes streams/sockets and drains actual work. Replacements requiring an already occupied fixed port fail safely; this layer does not invent socket transfer, shared ports or automatically restart an application. Use the existing host rolling/fleet boundary when needed. Protocol handlers enforce tenant, method/tool and resource permissions after endpoint authentication. Forwarding headers are not identity. Endpoint definitions, authorization and handlers are executable private plugin state, not browser configuration.

The typed JSON POST client createServiceClient<Input, Output> requires a fixed endpoint, transport(Request), an exact host allowDestination(URL) decision, response Standard Schema, timeoutMs, maxPayloadBytes, maxConcurrent and retry: { maxAttempts, idempotent }. Input is a caller-declared type and bounded JSON; output is validated/transformed by its schema. It is a JSON endpoint client, not a generated Connect/JSON-RPC/WS/gRPC client. JSON-RPC envelopes, if used, belong to the declared input/output types and schema.

Transport injection is deliberate: the host owns egress, DNS rebinding protection, TLS and connection policy. A URL/origin predicate is not a DNS/IP firewall. For native Node Fetch use an explicitly configured transport/dispatcher under that policy; see Node Fetch. Redirects are requested as errors, and redirected/mismatched response URLs are refused. Never accept destinations or outbound credentials from request payloads. Optional headers() supplies host-owned authentication without logs; hop-by-hop, authority and forwarding overrides are refused. No external network request occurs until call(input, { signal?, deadline? }).

The earliest caller deadline and local timeout applies to headers, all attempts, body reads and validation. x-zerux-deadline carries that absolute Unix-ms deadline; zhost validates it and caps it at its local request policy before exposing RpcContext.deadline/signal. A caller can shorten the budget, never extend it or gain authorization. Expired/malformed values yield 408/400. Connect/RPC/MCP handlers must pass the signal/deadline to their actual database/provider operations. This is a small propagation convention, not an authenticated distributed clock protocol. Established SSE and WebSocket lifetimes keep their zhost-specific ownership rules.

Request/response payloads have 16 MiB maximum configurable byte limits, JSON depth 16 and 10000-node limits before dispatch (response bytes are bounded before its schema runs); concurrency is at most 1024 and local timeout at most 120 seconds. Use plain JSON data without getters/toJSON hooks or executable values. Failed, oversized and cancelled response readers are cancelled/released. close() rejects new calls, aborts active calls and drains real settlement. Uncooperative transports, header callbacks, schemas or handlers can delay settlement; cancellation does not claim to forcibly kill JavaScript, undo a remote write or free pending work early.

Retries are explicit: 1–3 attempts, with more than one allowed only when the caller declares the operation idempotent. Transient transport failure and 502/503/504 may retry within the same total deadline. All other statuses, schema failures, body limits and cancellation do not retry. There is no automatic idempotency-key store or non-idempotent replay; an unknown write outcome remains unknown. Retries have no background queue or unbounded backoff and retain the same concurrency slot.

Pinned transactional outbox hook#

createTransactionalOutbox<Event>(database, { enqueue(transaction, event, context) }) requires the database facade's real transaction and transactionCapabilities(). Unsupported connectors reject before work. run((transaction, enqueue) => ..., options) passes through database-owned TransactionOptions, including cancellation, deadline, isolation and timeout negotiation. Business operations and the writer must use that exact callback TransactionDatabase; the hook never starts an independent journal transaction or publishes external messages. Do not perform provider/network side effects inside the transactional callback.

The host's writer inserts a durable outbox row on the supplied pin, with application idempotency/event schema and tenant policy. Opt-in GraphQL#

Import registerGraphQL and its types from zeruxjs/graphql, not the root. The integration declares optional graphql@16.14.2 (GraphQL.js, MIT) and graphql-sse@2.6.3 (MIT). ts
import type { ZeruxPluginApi } from 'zeruxjs';
import { registerGraphQL, type GraphQLOptions, type GraphQLResolver }
  from 'zeruxjs/graphql';

type Policy = Pick<GraphQLOptions,
  'authenticate' | 'authorizeField' | 'authorizeData' | 'protectMutation'>;
const me: GraphQLResolver<unknown, Record<string, never>, string> =
  (_source, _args, context) => context.principal.subject;

export function registerGraph(api: ZeruxPluginApi, policy: Policy) {
  return registerGraphQL(api, {
    name: 'account-graph', path: '/graphql', ...policy,
    typeDefs: 'type Query { me: String! }',
    resolvers: { Query: { me } },
    introspection: false,
    persisted: { required: false, operations: {} },
    limits: { maxDepth: 6, maxComplexity: 500, maxAliases: 16,
      maxConcurrent: 16, timeoutMs: 3000 },

Supply real host policies before calling this from an awaited entry/plugin. The integration snapshots those fields per operation. authorizeField(context, info, source, args) must return exactly true for each registered object field, including nested subscription results. authorizeData receives principal, loader name, key and optional returned row; it runs before cache lookup and again for newly loaded rows. These hooks must enforce actual field/resource/tenant policy, and data sources must bind queries to the verified tenant. The library cannot infer database tenant columns or grant permissions. Build-time server/client classification#

buildProjectSources/zerux build now parse module syntax with installed TypeScript before publishing staged output. They classify server, client and shared modules, following relative imports, re-exports and literal dynamic imports transitively. A directive is recognized only as an exact unescaped 'use client'/"use client" or 'use server'/"use server" string in the leading directive prologue (comments and earlier directives are fine). Strings/comments/templates after executable statements do not declare a boundary. .client.* and .server.* filenames are explicit conventions; conflicting declarations reject. Entry/plugin/controller/ middleware roles and HTTP/default route exports remain server-owned. Browser entries are excluded from server route execution, including explicit directive entries during development discovery.

Unmarked helpers used by both partitions are shared. Client-only modules and helpers emit only as browser assets, while shared helpers retain their private server output too. Tracked relative server-to-client entry imports reject because no RSC/island cross-runtime protocol is implemented. Build classifications are not authentication or authorization, and use server creates no RPC/action endpoint. Development is still the Node module loader; full transitive browser checks and browser assets belong to the staged build, not an implied dev frontend bundler.

Prebundled browser assets may contain local CommonJS wrapper data such as state.exports and {exports:{}}. These are data properties, not permission to use free exports, module, require or globalThis.exports in client code. Client graphs reject Node built-ins/globals, server-only module labels, server service imports, unresolved/out-of-build relative imports and nonliteral dynamic imports. Explicit type-only imports are erased and do not authorize a runtime import. The current browser emitter supports a closed local ESM graph; bare packages, import aliases, JSON/CSS/SFC loaders and external URLs require a separate verified bundler contract and reject here. In particular React/Vue/Zyro browser package imports are not automatically bundled. Server JSX keeps the prior compiler behavior; Vue/other JSX compilation requires an explicit host transform. There is no automatic JSX-runtime selection based on a renderer name.

ProjectBuildOptions.transform(source, file, {environment}) remains an optional trusted compiler seam. Browser transforms must emit ESM JavaScript. Their output is checked again for server globals/imports, so an injected Node import cannot bypass the source graph check. The checks are a conservative static policy, not a sandbox for malicious JavaScript, a typecheck, a proof of dependency publication or a detector for arbitrary hardcoded secret strings. Keep credentials in explicitly server-only modules/configuration and never put them in public sources. Existing HTTP auth/tenant/consent boundaries still apply independently.

Diagnostics carry ModuleBoundaryError.code and the actual project-relative import chain, for example components/page.client.ts -> lib/shared.ts -> lib/db.server.ts. No credential values or absolute build paths are included. Module parsing is bounded at 5000 script inputs, 64 MiB total script source, 1 MiB per script and import depth 64; existing non-code build file/total budgets still apply.   • build-manifest.json: existing source counts/digest/directories plus renderer manifest pointers; old schema-1 production manifests remain accepted.
  • server-manifest.json: private, mode 0600 inside the private build tree; module source hashes, partition labels, local edges, private server-file paths and optional client-asset URLs. It contains no source text or request data.
  • public-assets.json: a safe projection with only module entry URLs and asset URL/integrity/byte/kind records. It contains no server configuration, module import chains, local source paths or automatic hydration data.

Browser modules are emitted under the first configured public directory at /_zerux/client/<graph hash>/<opaque module id>.js. Local imports are rewritten to actual emitted ESM assets; hashes include compiled graph content. The existing public-file handler serves them after production structure resolution. Static asset projection respects configured public-directory precedence. Generated-path collisions reject, and client-only app files are not imported by staged route discovery. Neither manifest is automatically injected into HTML or exposed as a diagnostic endpoint. A failed compile/boundary check removes its staging directory and retains the previous complete build. This is an extension/static HTML and local ESM foundation, not React Server Components or full Next.js compatibility.

Registered server actions and forms#

zeruxjs/actions is an opt-in server-only entry. Explicitly register an allowlisted schema, authorization callback and database write; exported functions are never discovered as remote calls. attach(api) installs exact opaque routes and generation cleanup, preflighting collisions and rolling back partial attachment. References are HMAC-derived for this application's origin/path/name. Shared instances must use the same private 32-byte application key and registration names. References are not authorization. Importing this entry from a client graph is already rejected by the compiler's server-service boundary. Only HTML form URLs and signed hidden fields cross the boundary; no closure, server source or credential is serialized.

Declare the optional @zeruxjs/validator and @zeruxjs/security peers when using actions. zeruxjs/action-stores/sqlite exposes a separate SQLite helper using the optional @zeruxjs/db-sqlite peer; it imports no native driver on its own. Core/browser navigation do not import these optional server entries.

The host must supply verified identity and a durable action journal. This minimal plugin is complete at the framework boundary: its arguments are private host-owned services, not values accepted from the browser. authenticate should map an existing createSharedAuth().verifySession(...) result (or another verified session) to the principal; resolve its account binding server-side, never from submitted tenant data.

ts
import type { ZeruxPluginApi, ZeruxRequestContext } from 'zeruxjs';
import type { TransactionDatabase } from '@zeruxjs/db';
import type { CsrfTokenManager } from '@zeruxjs/security';
import { escapeHtmlAttribute } from '@zeruxjs/security/encoding';
import { strictObject, string, pipe, minLength } from '@zeruxjs/validator/schemas';
import { createFetchRoute } from 'zeruxjs/fetch-route';
import { createActionRegistry, renderActionFields,
  type ActionStore, type ActionPrincipal } from 'zeruxjs/actions';

export function registerNoteActions(api: ZeruxPluginApi, host: {
  key: Uint8Array;
  csrf: CsrfTokenManager;
  store: ActionStore<TransactionDatabase>;
  authenticate(request: Request, context?: ZeruxRequestContext): Promise<ActionPrincipal | null>;
  canWrite(principal: Readonly<ActionPrincipal>): Promise<boolean>;
  invalidateTenant(tenant: string, signal: AbortSignal): Promise<void>;
}) {
  const actions = createActionRegistry({
    origin: 'https://app.example', key: host.key, csrf: host.csrf,
    store: host.store, authenticate: (request, context) => host.authenticate(request, context)
  });
  const save = actions.register('save-note', {
    schema: strictObject({ tenant: string(), note: pipe(string(), minLength(1)) }),
    authorize: async (input, context) => input.tenant === context.principal.tenant &&
      await host.canWrite(context.principal),
    async write(tx, input, context) {
      const result = await tx.insert({ table: 'notes', values: {
        tenant: context.principal.tenant, note: input.note
      }});
      if (!result.ok) throw new Error('Persistence failed');
    },
    successRedirect: '/notes/new',
    invalidate: context => host.invalidateTenant(context.principal.tenant, context.signal)
  });
  actions.attach(api);
  api.addRoute({ pattern: '/notes/new', method: 'GET', handler: createFetchRoute(
    async (request, context) => {
      const principal = await host.authenticate(request, context);
      if (!principal) return new Response('Authentication required', { status: 401 });
      const form = actions.form(save, principal);
      return new Response(`<!doctype html><html><head><title>New note</title></head><body>
        <form id="note-form" action="${form.action}" method="post">
          ${renderActionFields(form)}
          <input type="hidden" name="tenant" value="${escapeHtmlAttribute(principal.tenant)}">
          <label>Note<input name="note" id="note"></label>
          <span id="note-error"></span><button>Save</button>
        </form></body></html>`, { headers: {
          'Content-Type': 'text/html; charset=utf-8', 'Cache-Control': 'no-store'
        }});
    }) });
  return { actions, save };
}

Failed forms return sanitized HTML with status 4xx/5xx, fixed messages and schema-declared field paths; private values are not echoed. Keep existing host CSP/security headers on the form page. The configured origin is independent of Host/forwarded headers. Every invocation, including a committed replay, authenticates, verifies exact origin and session-bound CSRF, validates input and authorizes the tenant/operation before consulting persistence. The initial transport deliberately accepts only POST URL-encoded forms. JSON and multipart/file requests return 415; the file allowance is zero. Repeated fields, including reserved hidden fields, reject instead of silently selecting a value. Schemas control unknown fields/coercion; use strictObject when extras must reject. Defaults are 32 KiB body and 128 KiB canonical data, 64 fields including the two hidden fields, 32 unsettled operations and a 10-second cooperative deadline. Body limits can rise to 128 KiB, fields to 200, active operations to 1024 and deadlines to 60 seconds. Validated output must be inert bounded JSON (24 levels/2000 nodes); it is cloned and frozen before authorization/writing. Durable action journal and transaction ownership#

createPinnedActionStore({ transaction, journal }) consumes the existing @zeruxjs/db DatabaseTransaction, not a second transaction system. Unsupported connectors must reject before use; use their negotiated pin. The journal explicitly declares durable: true (including physical persistence, not an in-memory SQLite database) and implements:

  • reserve(tx, claim): atomic create-if-absent on the unique hashed key, or return pending, committed or conflict after comparing the exact input digest.
  • finish(tx, claim): exact-owner/digest pending-to-committed CAS with an exact affected count. It must run on the supplied pin, together with the business write.

The first transaction durably reserves the claim. A separate transaction runs the business write and completion record on one connection/session. A concurrent claim never enters the write. If the second transaction fails or its commit is indeterminate, the durable reservation stays blocked; it is never automatically reclaimed/retried. A lost acknowledgement may have left a committed record: a freshly authorized replay confirms that record and reruns only idempotent cache invalidation, not the mutation. Same key with different validated input conflicts.

createSqliteActionStore({ transactionSync, journal }) from zeruxjs/action-stores/sqlite instead consumes the existing SQLite SqliteConnector.transactionSync. Both journal methods and the action write must be synchronous; declared async writes reject during registration, and returned thenables reject inside the guarded transaction. There is no await across BEGIN/ COMMIT and no conversion of SQLite's unsupported async transaction capability into a claimed supported feature. Both factories borrow the transaction/journal; registry shutdown never closes the host's database. Journal types stay with this framework integration; driver/pin types stay owned by their database packages.

Production journals are an explicit prerequisite: create their unique constraints through host migrations, enforce bounded row quotas, retain records until signed key expiry, and own durable storage/backup/cleanup. Ordinary cache get/set or an in-memory map does not satisfy action-atomic-v1. Journal expiry includes the declared maximum inter-instance clock skew (default five seconds, configurable 0–60 seconds); never purge earlier. Keys are HMAC-bound to application, action, principal, tenant and nonce; stored fingerprints contain no submitted values. Default signed-key lifetime is 15 minutes (configurable 1 second–24 hours). Expired keys reject before dispatch even if the journal has purged them. Pending/uncertain records may be reconciled only with durable proof; never reuse their signed key to repeat an uncertain external effect. Keep clock differences within that declared bound. Changing the private application key invalidates references/forms; coordinate changes across instances.

Writes are database-only. External email/payment effects require a real transactional outbox/host reconciliation contract, not an awaited network call inside this write. Invalidation runs only after confirmed persistence, has its own bounded cooperative signal (at most five seconds), and must be idempotent because committed replays can repeat it. A crash between commit and invalidation still needs an outbox/reconciler or cache expiry; this helper does not promise durable cache delivery. Cancellation retains active slots until actual callbacks/driver work settle. No Promise timeout claims forced cancellation or rollback. The native disposable SQLite/WAL checks and simulated acknowledgement failure do not establish live PostgreSQL/MySQL/provider or real-browser acceptance.

No hosting vendor configuration is guessed or deployed automatically.

mode: 'mixed' exports the same selected public pages but marks unlisted URLs as node-server-required. Configure the host to serve those files and route remaining requests to the existing Node application, where authentication/actions still run. A file-only host cannot run those functions. The real 404 artifact remains available; the Node application's own errors and hosting precedence remain host-owned. There is no universal SPA fallback and no serialization of a server runtime into HTML.

Budgets, staging and failure behavior#

Defaults: 1000 concrete routes/redirects (plus the 404), 32 MiB total output, 1 MiB per HTML page, 30 seconds per export and 5 seconds per enumeration/render. Limits cap at 10000 instances, 512 MiB total, 16 MiB per page, five minutes total and 30 seconds per route operation. There are at most 256 route definitions, 1000 selected assets, 5000 public-data nodes and 24 public-data levels. Callbacks are sequential, signals are cooperative, and iterators/scoped cleanup drain before release; a Promise timeout never claims forced JavaScript cancellation.

Output is staged inside the project under the output parent. Shared build path guards reject source/output overlap and symlinked parents; file reads reject links and validate integrity. An exclusive per-output lock rejects concurrent exports. Only an owned, unedited previous export may be replaced. Enumeration, validation, render, resource-disposal and budget failure leave it intact; staging/locks are removed on normal failure. Completed candidates are promoted with the existing same-filesystem rename/backup/rollback pattern, not published or deployed. This is not a crash-atomic deployment transaction; readers should consume completed output, and a crash may require inspecting/removing a stale lock/backup manually. Project files must have a trusted exclusive writer; this is not isolation against a hostile process racing filesystem changes. Normal zerux build/start and the docs exporter remain separate.

Explicit queue backend selection#

Legacy queue:{enabled:true,redis,queues,workers} remains BullMQ-specific. Opt in to the backend-neutral facade with queue:{enabled:true,required:true,selection} from selectQueueBackend in @zeruxjs/queue/neutral. Construct the selection with a trusted explicit factory from @zeruxjs/queue/backends; see the queue example and capability matrix. No packages are scanned or loaded from request configuration. Backend options/required capabilities validate before database/cache connections, and mixing selection with legacy queue settings rejects. All options/factories remain private.

Each generation owns the selected backend. Partial startup runs its registered cleanup in reverse order; a required failure rolls back cache/database too. An optional failure degrades with a fixed, secret-free warning and retains the cause only in trusted scope diagnostics. On shutdown queue resources close before cache/database. Native processor settlement/grace policies remain backend-owned; no forced JavaScript cancellation or automatic restart is inferred. The neutral BullMQ path does not mount dashboards; use the unchanged legacy configuration for native dashboard routes.

Explicit named search service#

Set search: { enabled: true, registration }, where registration comes from registerSearchService in @zeruxjs/search/adapters. Search is a supported built-in service and a valid custom-service dependency; it is not a root index-signature extension. Registration validates before provider acquisition, starts inside the generation, and closes in reverse service order. Enabled search failure rolls back the candidate. Search callbacks/endpoints/credentials remain private; no HTTP route or active global manager is installed. Register only trusted factories, authorize each operation from verified host identity, and propagate request cancellation. See search adapter contracts and example.

Opt-in route data cache#

zeruxjs/route-data-cache exports createRouteDataCache and routeDataCacheKey; imports allocate no cache or listeners. See the executable public-import example. A host owns one coordinator per application generation and borrows a scoped CacheManager. Close the coordinator before the manager. This entry is server-only; it does not automatically cache routes, responses, headers or cookies.

Keys hash application, verified tenant, optional verified principal, registered route ID, exact path, sorted parameters and locale. Supply every data dependency in these fields; do not cache permission-dependent data without a principal. The host must derive scope after authentication/authorization. Query strings, headers and cookies are deliberately not inferred as trusted cache dimensions. Cached values must be bounded plain JSON; no class instances/accessors/functions. Never put secrets in an explicitly public result. Public opt-in rejects principals. result.response() uses existing cached/ETag handling, defaults to no-store and only permits public max-age for explicitly anonymous public data. Stale output is no-store, so it cannot reset a shared freshness window. HTTP validators remain content-derived. Route authorization always runs before this helper.

freshMs is 1–86400000; staleMs is an additional 0–86400000 window. At the fresh boundary a stale read starts one process-local refresh and returns old data; a failed refresh never extends freshness. At the stale boundary readers await a refresh. Cache outages reject without silently invoking the producer. Default bounds: 1024 metadata entries, 16 unsettled reads/refreshes, 1 MiB JSON, 32 levels and 32 tags. Evicted metadata disconnects its storage key; entries have backend TTLs rounded up to seconds, while exact freshness uses stored timestamps. Policies changing for a key retire the old entry. Set development:true to bypass reads deterministically; writes/invalidation and budgets retain the same rules.

invalidate({tenant,tag}) or invalidate({tenant,path}) matches exact paths/tags within this application's verified tenant. These are cache tags, unrelated to @zeruxjs/tags tracking containers. Invalidation retires local metadata before returning. In-flight reads/refreshes reject if retired; each entry has a unique storage address, so a late backend write cannot populate its replacement. Old bytes expire naturally; invalidation does not promise physical erasure. Use the existing action definition's post-commit invalidate callback; do not invalidate before confirmed persistence. No management HTTP endpoint is installed: hosts own fresh authorization, CSRF/origin controls and rate limits at that boundary.

Coordination is explicitly process-local even with Redis backing. Each coordinator uses a private random namespace: no cross-process reuse, distributed invalidation, locks or durability are claimed. coordination:'distributed' rejects because the cache contract has no atomic fencing primitive; conditional set/counters alone do not prove eviction-safe invalidation. capabilities exposes borrowed provider metadata without upgrading unknown guarantees. Memory remains volatile.

Caller cancellation stops that caller waiting, without aborting a coalesced job needed by another caller. Producers receive a coordinator deadline/AbortSignal; timeout and close signal cancellation but cannot force JavaScript or native cache operations to settle. Slots remain occupied until actual settlement, and close awaits all owned work, preserving borrowed cache ownership. Noncooperative work can therefore delay close. No background timer/scheduler or production Redis/live browser qualification is implied.

HTTP policy terminology follows RFC 9111. Application data invalidation does not purge a browser/CDN response already cached under an explicit public policy; choose a conservative HTTP max-age separately.

Coordinated privacy operations#

zeruxjs/privacy is an opt-in Node-only headless coordinator for host-authorized subject exports/erasure. Importing it starts no jobs, routes, service discovery or provider calls. Public example injects private stores and participants. Register it as an explicitly declared custom service, return close as its disposer, and declare service dependencies so it drains before those stores. No new root config key, automatic HTTP API or global manager is introduced.

The host must supply a verified account-linkage resolver, per-operation tenant/ subject authorization, approval-evidence verification and a versioned privacy policy. Email alone, caller roles, hashes or a job ID never prove identity. The resolver returns opaque tenant/subject references; authorization runs on create, inspect, preview, approve, resume and download. Check HTTP authentication and Origin/CSRF at the host write boundary; callbacks are not a substitute for it. Hashes/linkable references remain personal data under applicable host policies.

Preview, approval and crash behavior#

Create a tenant/subject-bound job, then call preview repeatedly (one participant page per call). Preview calls only read-only discovery; it never invokes execute or writes export data. Counts are bounded live observations, not a database snapshot. Show the complete plan/holds/limitations before approval. Approval binds job, scope, operation, policy version, participant versions and preview summary by hash; the host verifier returns only an opaque evidence reference, actor and expiry. Evidence bodies and deleted payloads never enter checkpoints. Expired approval/jobs fail closed; this initial API does not silently renew approval or reset an uncertain job.

After approval, each resume processes at most one page. PrivacyJobStore must provide current tenant-keyed reads, linearizable create/CAS with unique revisions and an atomically retained metadata-only revision journal. It must be durable, private and subject to host retention/hold policy; no in-memory production fallback is supplied. Store checkpoints/cursors privately: opaque cursors can be linkable. Preview failures retain failed/UNAVAILABLE; effect/checkpoint uncertainty retains running or uncertain without advancing the cursor. Error messages/codes are fixed; private causes exist only for restricted host diagnostics.

Participant receipt requirement: execute must atomically persist a durable, idempotent page receipt with its local effects under pageKey. It must recheck subject/tenant authorization and retention holds immediately before modifying data. recover returns that exact completed receipt or null for unresolved/in-flight work; it must not repeat effects. A crash after commit but before coordinator checkpoint therefore recovers the same page. A null recovery stays uncertain indefinitely until host reconciliation establishes its outcome. Ordinary cache get/set, a local Set, or an external API success without a durable receipt cannot implement this contract. Do not declare a participant capable if its store/provider cannot supply it. Distinct stores do not share a transaction; no global atomic erasure or automatic legal compliance is claimed. Concurrent invocations contend on checkpoints, not on arbitrary process locks. No expired lease is guessed safe to steal.

Each page rechecks authorization; revoked access stops further dispatch/download. Successfully processed records, retained holds, unsupported providers and uncertain work remain distinguishable. A job finishes partial if holds or outside-scope records remain, even when all local operations finished. Hold evaluation belongs to the participant and declared host policy. New/concurrent records can change counts; approval authorizes the bounded subject scope, not a frozen list of record IDs.

Private portable exports and resource budgets#

Exports are JSON Lines with {participant,record} envelopes. A required host projection approves export fields; a bounded JSON encoder rejects secret key names, non-JSON objects, excessive nesting and oversized values. This cannot detect a secret intentionally hidden under an innocent field name. Export only authorized subject data and redact third-party information. Erasure receipts cannot carry payloads; checkpoints store only scope, approval, coverage, cursors, counts and codes. For optional host CSV views use privacyCsvCell to quote and neutralize formulas; JSONL itself does not interpret spreadsheet content or HTML.

PrivacyExportStore.putPage privately persists immutable, idempotent page bytes before checkpointing; same key/different bytes must fail. Participants' recovered export receipts must preserve the same data. The export store independently enforces tenant/job access, expiry and private cleanup/retention, and returns ordered bytes through read, never public URLs. Downloads require a terminal completed/partial export, check access/expiry for every chunk and cap total bytes. Host responses must use private/no-store, attachment disposition, nosniff and the JSONL content type. Already delivered bytes cannot be revoked or recalled.

Defaults: 16 participants maximum, 50 records/page (maximum 100), 1000 pages per participant (maximum 10000), 4 pending operations (maximum 16), 5-second cooperative operation/download deadline, 24-hour job lifetime, 1-hour export expiry and 10 MiB export ceiling (maximum 100 MiB). Export pages/chunks cap at 256 KiB. Jobs expire within 7 days. Limits are validated and no unbounded background scan/retry is started. Streams follow consumer backpressure. Callers must close/return download iterators on disconnect. Signals cannot force-stop arbitrary adapters or roll back committed writes; slots and close() wait for actual settlement. close() aborts owned scopes and drains them, but never closes borrowed job/export stores or participant services.

Synthetic checks: node --test test/privacy.test.mjs after building. They exercise preview-only behavior, holds/tenant separation, approval/revocation, lost checkpoints, uncertain recovery, private export/expiry, secret rejection and cleanup. No real user data was deleted. Production durable stores/receipts, account proof, legal policies, provider/backups reconciliation and host HTTP/browser integration remain prerequisites.

Loader integration: standard file:, node: and data: imports delegate to Node resolution before custom path aliases. Alias validation still rejects unsafe custom names; standard URLs are not private registry keys.

Development hosts can set server.watchIgnoredPaths to at most 64 validated project-relative directories, for example [".workspace"]. These private paths are omitted from public config and passed to zhost before source traversal; the service runtime directory is excluded automatically. No absolute paths or traversal segments are accepted. This is watch policy, not filesystem authorization.

Trusted plugin observers may borrow an explicitly configured lifecycle bus with api.lifecycleHooks?.(). Its optional result is never included in getConfig() or public manifests. Remove every registration token through api.onDispose; plugins do not own bus replacement or disposal.

The CLI dev and build loaders opt into project-scoped source resolution: missing local .js, .mjs and .cjs imports can resolve to .ts, .mts and .cts siblings. Existing JavaScript always wins; package dependencies, paths outside the selected root and production start do not use this fallback. Programmatic users can opt in through registerLoader('zerux', {sourceRoot}) from zeruxjs/loader. Native Node TypeScript stripping still applies, so this is not support for JSX, enums or parameter-property compilation.

Set server.portless: false for direct loopback HTTP without starting or changing the shared portless proxy or its aliases. The default remains true for existing consumers. Proxy state recovery and certificate trust remain explicit operator operations; an unverifiable PID marker is never silently discarded.

Legacy theme bootstrap code is static; cookie-name/default settings travel as inert UTF-8 base64 data on its script element. Runtime metadata is read through a bounded descriptor. Explicit host environment files retain symlink-based secret rotation support and are limited to 1 MiB each; their contents are never logs.
