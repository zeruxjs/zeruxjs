Development tools and module registration

Set up zforge with explicit lifecycle, typed public APIs and deployment boundaries.

↗ View Markdown

Installation and integration path#

sh
npm install zforge@0.0.4

This package has its own public API. Installing it does not create an automatic runtime service key in zerux.config.js. Use the framework integration described below or initialize it in the tool/application that owns its lifetime.

Worked TypeScript setup#

ts
import { registerSharedDevApp } from 'zforge';
type Registration = Parameters<typeof registerSharedDevApp>[0];
const options = { appName: 'example', appPort: 3000, rootDir: process.cwd() } satisfies Registration;
// The host owns startup and teardown when registering this application.

JavaScript can use the same runtime APIs without type-only statements. Enable JSDoc checking if editor validation is desired; a transpilation step alone does not typecheck the input.

Usage and configuration#

Zforge supplies shared development registration, client injection and module definitions used by the server orchestration layer. Ordinary Zerux applications normally configure their development modules through the framework rather than creating another shared server manually.

Module API/socket handlers run trusted application code. Validate origin/host and request size at the real development-server boundary; development is not permission to expose tokens or arbitrary filesystem operations to a network. Only inject the development client into responses belonging to that controlled development environment.

Public types#

ts
import { registerSharedDevApp } from 'zforge';
type Inputs = Parameters<typeof registerSharedDevApp>;
type Result = Awaited<ReturnType<typeof registerSharedDevApp>>;

Use installed public declarations and validate untrusted runtime values separately. Avoid deep source imports; the manifest reference below records the actual exported entry points for this version. Generic helpers may preserve a more useful concrete type at the call site than a broad ReturnType alias.

Failures, ownership and production use#

Avoid duplicate global registrations during reload. Use the owning module/server lifecycle and unregister callbacks where available. A shared server is a development convenience, not a public production reverse proxy. Test request abort/size limits, host matching, module loading failure and browser disconnect. Keep source paths and application metadata out of unrelated public sites.

Verify the integration#

Run the real owning application/tool with a normal input and a failure input. Inspect exit status or typed results, then verify cleanup/restart and the installed production entry point. A successful docs build does not exercise child processes, browser APIs, sockets or filesystem permissions on every supported operating system.

Explicit transport module ownership#

The optional zforge/modules entry accepts an injected zhost/protocols kit and mandatory host authentication. It supports actual SSE /events and the existing stateless HTTP MCP tool subset at /mcp; native gRPC declarations reject before startup. Each endpoint declares exact origins, bounded messages/concurrency/time and public output fields. Loopback/forwarded headers never authenticate a caller. A supplied Origin must match; non-browser clients still require authentication.

Await module disposal or host close. Reload disables and drains the previous module before starting its replacement, closing old sockets/streams; failed replacement leaves the module unavailable. Signals are cooperative and teardown waits for real handler settlement. Legacy shared UI/HTTP/WS module registration remains separate.

zforge/diagnostics accepts real framework RequestSpan records through an optional TracingAdapter. Per-app count/byte/TTL caps and generation fencing bound retention. Headers are MIME/length only, bodies default to omitted, and normalized error codes exclude causes/stacks. Host authorization remains required when mounting its escaped request table. The package README and examples/modules.mjs describe the public integration; importing either entry starts no server. Node ephemeral HTTP fixtures are not browser, remote TLS or full MCP/gRPC qualification.

Development experiment controls#

zforge/experiments returns a registered MCP module over the shared deterministic ztrial/experiments API. Production mode rejects. Explicit host authorization is required for inspection, preview and named test callbacks; mutations also require POST, exact Origin and host session-bound CSRF verification. Client role/group or subject strings never grant overrides.

Previews are expiring display-only results, capped at 60 seconds and the current credential/deadline. They do not write assignments or emit analytics. The separate stateless evaluator preserves consent/tenant/environment gates; durable preserve history is deliberately unsupported. Audit metadata excludes private traits and raw callback output. Dispose/reload drains the generation and closes the evaluator. The package's examples/experiments.mjs demonstrates public imports and explicit policies. Host authentication/audit durability and browser UI remain integrations that require their own acceptance checks.

Clean source builds#

The repository build planner compiles zforge's independent strict core first, then its hosting/framework owners, then the normal full strict package build. This explicit manifest metadata resolves declaration cycles for optional integrations; it does not create runtime services. Use node scripts/build-workspaces.mjs --scope zforge in a checkout. The intermediate build:core does not certify the full archive. Published consumers still select the actual optional peers and own host authorization and teardown.

Full package README

zforge#

The internal development toolkit for Zdev. zforge provides the foundational infrastructure for developer tools, including the shared dev server, dev-client injection, and the devtools module registry.

Core Capabilities#

  • Shared Dev Server: Orchestrates a single devtools server that can handle multiple Zdev applications simultaneously.
  • Client Injection: Automatically injects development scripts and overlays into HTML responses during development mode.
  • Module Registry: A flexible system to register and manage devtools modules, complete with API and WebSocket handlers.
  • Event Bus: A robust event broadcaster for hot-updates and real-time communication between the server and the browser.
  • Security: Integrated with @zeruxjs/security to ensure devtools access is authorized and safe.

Key APIs#

App Registration#

typescript
import { registerSharedDevApp } from 'zforge';

const devInfo = await registerSharedDevApp({
    appName: 'my-app',
    appPort: 3000,
    rootDir: process.cwd(),
    devtools: { modules: [], frameAncestors: ['http://localhost:3000'] }
});

Client Injection#

typescript
import { injectDevClient } from 'zforge';

const polyfilledHtml = injectDevClient(originalHtml, {
    routeName: 'my-app',
    serviceName: 'dev',
    devPortLessAlias: { value: null },
    devServerUrl: 'http://localhost:4000'
});

Module Definition#

typescript
import { defineDevtoolsModule } from 'zforge';

export default defineDevtoolsModule({
    name: 'my-module',
    // ... config and handlers
});

Internal Architecture#

zforge is designed to be the "brain" behind the Zdev development experience. It manages the lifecycle of the dev server and provides the bridge between the framework's internal services and the developer-facing dashboard.

<p align="center"> Part of the Zdev Monorepo. </p>

Request boundaries#

The HTTP devtools server enforces a 1 MiB streamed request-body limit via src/request.ts, with cleanup on completion, failure, or aborted requests. Local development hostname checks reject crafted authorities. Focused tests: node --test test/request.test.mjs after building. Devtools should be restricted to trusted networks; configure firewall and proxy access appropriately.

Security and live reload diagnostics#

The shared development server is loopback-only by default. To listen on a different interface, set ZDEV_BIND_HOST only with trusted access controls, such as an authenticated reverse proxy. Devtools and its APIs are not an Internet-facing administration service.

State and registry JSON files are private, bounded, atomic and reject symlink destinations. Client HTML injection escapes script-breaking values. Snapshot and bootstrap JSON include a reload status object containing the attempt count, generation and last failure message when available.

Document policy and framing#

Development devtools pages allow same-origin framing by default. Cross-origin embedding now requires exact canonical origins in the registration's devtools.frameAncestors list (HTTP(S), no wildcard/path/credentials). Registration validates the list before writing registry state. Existing allowedDomains routing rules and untrusted Origin/Referer/Host headers never grant framing. Configure the parent application's frame-src separately; both sides must permit the embed.

createDevtoolsDocumentPolicy({mode, frameAncestors}) is a public, side-effect-free per-document helper, defaulting to production. Each call returns fresh nonce and frozen headers. The server uses development unless NODE_ENV is production; production ignores all development framing grants and keeps frame-ancestors none, XFO DENY, COOP same-origin, COEP require-corp and CORP same-origin. Development explicitly allows inline UI styles/data images/fonts and uses COEP unsafe-none to support the development document; these choices never follow a browser error or request header. No development server access/authentication is implied by a framing grant.

Manual injectDevClient accepts an optional trusted response-owned nonce. It validates and attribute-escapes that nonce without inspecting/replacing CSP. The application must approve required styles, WebSocket connections and devtools frames itself. Nonced scripts do not automatically authorize dynamically created styles or inline style attributes. The shared document renderer uses the same nonce as its response header. Reuse it only within that response, including streamed chunks. Zhost's automatic injector skips enforced-CSP and explicitly flushed responses. See security policy ownership. Run node --test test/framing-policy.test.mjs test/state-injection.test.mjs after building; these are Node checks, not browser framing/isolation verification.

Scoped transport modules and request diagnostics#

zforge/modules is an explicit opt-in host, separate from the legacy shared UI, HTTP/WS registries and file module loader. Inject the actual zhost/protocols exports; type-only optional peers avoid a runtime dependency cycle. Merely importing these entries starts no listener. See public example.

Declaration Actual implementation Limits
sse zhost HTTP /events, bounded replay Server-to-client JSON update events; no client commands
mcp zhost HTTP /mcp Stateless JSON tool subset; not full MCP/stdio/subscription parity
grpc Unavailable Rejected before startup; a name is not an implementation

Every endpoint requires message/concurrency/time limits, a host authentication callback and an exact origin allowlist. Missing Origin supports authenticated non-browser clients; supplied Origin must match. Loopback is the default, not an authentication mechanism. Remote binds additionally require an explicit public origin and host-owned TLS/egress/access controls. Host is checked directly; forwarded headers never grant identity or proxy trust. MCP clients must advertise both application/json and text/event-stream. Each tool also authorizes its arguments against the initiating verified principal and receives cancellation and a deadline. The host must return a subject and expiry no more than five minutes away. Connections expire at the earlier auth expiry/endpoint timeout; reconnect requires fresh authorization. There is no silent authorization refresh.

Endpoints own separate listeners; addresses are returned after startup. Duplicate binds fail through zhost registration/startup. Setup disposal callbacks run LIFO. Startup failure rolls back listeners and acquired setup resources. Replacement first disables and drains the old module, closes streams/sockets and then starts the candidate; failed replacement does not resurrect privileged old connections. Dispose handles are generation-fenced. Await dispose, unload or host close. Cancellation is cooperative: teardown waits for actual handler settlement and cannot force-stop arbitrary JavaScript. No process supervision is added.

SSE history defaults to eight events (maximum 32), clients to the declared concurrency, and slow consumers are disconnected by zhost backpressure policy. Output is default-deny JSON: only explicit publicFields survive, sensitive key names always disappear, and depth/size/count budgets apply. Approved field values must already be public; field names cannot detect a secret disguised as a count. Responses are no-store. Do not use module endpoints as an unrestricted proxy.

zforge/diagnostics consumes the real zeruxjs RequestSpan/TracingAdapter contract. Activate each application generation or create its adapter, then pass that adapter to framework observability. Default retention is 100 records/256 KiB/15 minutes per explicitly named app; generation replacement clears old records and fences late exports. Route labels are allowlisted, headers retain only MIME/length, bodies are omitted unless the host explicitly approves primitive fields, and errors retain only normalized fixed codes. No request body stream is read or persisted. The optional section/table escapes output; mount/read it only behind host authorization. It does not install an auth layer in the legacy shared server. Existing private atomic state and script-safe client injection remain separate owners.

Focused Node checks: node --test test/*.test.mjs after npm run build. Ephemeral real HTTP/SSE/MCP fixtures cover denial, bounded replay, startup rollback, reload disconnect and real framework span export. These do not qualify browser UI, remote TLS/proxy deployments or native gRPC.

Development experiment inspection#

zforge/experiments supplies createExperimentInspectionModule, an opt-in consumer of the injected public ztrial/experiments evaluator. Register its returned module with createDevtoolsModuleHost; no global module or UI is silently replaced. See public example. The optional ztrial peer is type-only until the host injects its factory. Production mode rejects before acquiring resources.

The MCP tools are experiment.inspect, experiment.preview and experiment.test. They accept a declared experiment ID; preview additionally requires a declared variant and integer ttlMs (1–60000), test a host-registered test name (maximum 16). No source code, arbitrary role/group, subject, tenant or targeting traits are accepted. Host authentication identifies the operator; resolveContext independently binds that operator to the evaluation tenant/subject/environment/consent. The shared evaluator's denied decisions remain denied. Explanations expose only approved experiment/version/variant/algorithm/reason and finite variant weights.

Every tool requires host action authorization. Preview and test additionally require POST, an explicit matching Origin and a successful host verifyCsrf(request, context) callback. The module host still authenticates each request; loopback never bypasses these checks. Browser cookie sessions need real session-bound CSRF verification, not an always-true callback. Policy callbacks are trusted server code.

Preview returns previewOnly:true with expiry capped by the operator credential and request deadline. It is a display result, never installed in an assignment store or applied to production traffic. Consumers must discard it on expiry. There is no persistent override/capability token, background timer or production override API. Inspection owns a separate bounded stateless evaluator with recording disabled; store, recording and assignment override options reject. Consequently preserve catalog migrations requiring durable history are unsupported here and fail closed; this view does not claim to reproduce a production sticky assignment. Consent is still checked by ztrial, and no preview/test analytics are emitted.

Tests are explicit host callbacks, not test-runner discovery or arbitrary model/client commands. They receive cancellation and return only a boolean, with no raw logs or artifacts. Host code must cooperate with deadlines and avoid privileged side effects unless separately authorized. Required audit callbacks receive authorized/completed/ failed metadata with operator reference, application/generation/epoch, time and preview expiry, but no private evaluation identities, traits or payloads. Audit failure is explicit and prevents subsequent execution when it occurs before dispatch; a terminal sink failure cannot undo a test callback that already ran. Store audit records privately.

Create a fresh definition for every load. Setup acquires the evaluator; unload/reload aborts/drains handlers through the module host and closes its owned evaluator. Late results are rejected, old handles cannot dispose replacements, and imported definitions start no work. Existing custom sections/components can render these headless results; no browser dashboard or statistical significance claim is added.

Building from workspace source#

Use node scripts/build-workspaces.mjs --scope zforge from the repository root for a clean checkout. The manifest's repository-only workspaceBuild metadata selects build:core first, then builds the declared zhost/ZeruxJS owners and runs the normal full build. Both TypeScript configurations inherit strict checking. The core entry does not import the optional modules/diagnostics/experiments entries; the final pass must compile those entries successfully before the workspace build succeeds.

This resolves the source dependency cycle without duplicating transport/tracing types or adding eager runtime dependencies. build:core alone is an intermediate developer step, not a complete package/archive build. npm run build and prepack remain the full compiler check once prerequisite declarations exist. Invalid bootstrap metadata and either compilation-stage failure reject the build; the planner does not run applications or listeners. Optional peers remain host-selected for consumers of the compiled package.
