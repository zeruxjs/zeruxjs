# ZeruxJS development guide for AI chats and coding agents

This guide applies to AI chat assistants, IDE assistants and coding agents working on this repository. Follow the user's separately supplied task and delivery instructions. Use available tools honestly: distinguish proposed edits from applied changes, and report checks that could not run.

Read this file and the root README first. At the start of each new chat or agent session, discover and read all repository README files (case-insensitive, including nested package, application, tooling, vendor and license READMEs) to understand the ecosystem together. Exclude dependency installations, generated build output, caches and VCS internals. Read in manageable batches without silently truncating content; if access or context limits prevent full coverage, state which files remain unread rather than claiming completion. Then inspect the affected package/application manifests and implementation; README claims must be checked against source before changes. Within the same session, reread READMEs that changed or are relevant to the current task instead of repeating the entire scan. Keep related packages, public exports, shared types, plugin contracts and consumers compatible. Do not bump package versions, internal dependency references or release metadata unless explicitly requested.

## Current repository context

This section is a maintained orientation map, not a claim that every capability has been tested in the current session. Recheck the linked sources before relying on details that may have changed.

### Product and development priorities

- Primary development is under `packages/`: framework, library, services and tooling. Packages must work together while retaining their documented standalone contracts.
- `sample-packages/` contains private plugin/module examples for development; keep them private. `apps/` contains development consumers and documentation, not public library packages.
- Zenix now has a minimal SQLite domain core in `@zenixjs/core/cms`; `zenixjs/application` supplies an initial opt-in SSR CMS while `create-zerux-js` generates validated SSR projects; `create-zyro-app` generates standalone client/static/SSR/hydrated projects; `create-zenix-js` generates a JavaScript SQLite CMS scaffold requiring host auth/CSRF policies before startup. `zclivo` also retains its separate minimal starter.
- VS Code extension development is on hold. Do not expand extension scope unless requested.
- Development changes do not authorize publishing, version bumps, deployments or restarting user-managed applications.

### Runtime and package relationships

- `zeruxjs` directly depends on `zclivo`, `zhost`, `zlook`, `zforge`, hooks, database, cache and lint packages. Queue, validator, security, SQLite and parse5 integrations use optional peer contracts; selecting an integration still requires its dependencies and explicit host configuration. Inspect its [manifest](packages/zeruxjs/package.json) when changing foundational APIs.
- Framework orientation: `packages/zeruxjs/src/index.ts` defines root exports, `src/bin/zerux.ts` is the CLI entry, `src/commands/` handles server/build commands, and `src/bootstrap/` contains configuration, runtime, request lifecycle, services and workers. `src/loader/` and `src/compiler/` handle loading and watching.
- `zhost` owns hosting/proxy supervision and protocol gateway helpers, including MCP support. `zforge` supplies shared development tooling and depends on security helpers; `zlook` supplies watching. Do not reintroduce historical `zcli`, `zsrv`, `zwatch` or a separate MCP package based on old notes.
- `zhost/protocols` also owns inert application-scoped transport registration with reverse startup rollback, required-authorized HTTP/WS adapters, bounded cooperative work and an implementation capability matrix. Native gRPC service registration remains unavailable; HTTP/2 forwarding and external QUIC handoff are distinct from native transports. Adapter shutdown drains actual handler settlement; signals do not force-cancel JavaScript.
- Zhost proxy budgets optionally cap incoming TCP sockets, direct-peer concurrent work and upgraded WebSockets within the shared request ceiling. `getAdmissionStatus()` exposes fixed path/peer-free counters. Identity/compressed forwarding cancels its source on downstream close; partial upstream requests are never replayed. Drain deadlines are bounded to integer 0–300000ms; supervision/restart policy remains separate.
- `zyrojs` is the standalone signal/DOM/network library. Its `defineComponent` owns one-time setup per type/key, synchronous tracked renders and scoped cleanup; arrays are owned fragments, and allocating hooks during render reject. `ref` aliases signals, while DOM refs use callback/current holders; `watch` owns untracked callback cleanup. Async children/template compilation remain unsupported. `/server` supplies bounded V1 whole-root SSR with public-props validation and pure security encoders; `/hydrate` adopts versioned nodes with explicit mismatch policy, scoped cleanup and retained form edits. `/component` owns universal authored helpers and deterministic setup `useId`; trusted raw HTML requires a host sanitizer token and opaque leaf. Static SSR stays marker-free, selective hydration/textarea/foreign content remain unavailable, and real-browser qualification requires Playwright/Chromium. `@zeruxjs/zyro` is an observable bridge; its optional `/renderer` entry injects standalone primitives for explicit read/select/write conversions with mount/request scopes, batching and owned cancellable resources. Core imports remain independent of the optional ZyroJS peer. Source stores stay borrowed, async pending slots last until actual settlement, and stale refresh promises retain their legacy raw return semantics while state commits are fenced. React/Vue packages provide adapters. These are distinct APIs, not interchangeable runtimes or a complete framework hydration pipeline.
- `@zeruxjs/react` keeps core stores/injected hooks independent of React DOM. Optional `/server` and `/browser` entries lazily use matching host React/React DOM peers for native string SSR, mount/update/hydrate/unmount; `/hydration` is an ESM-only bounded public-state codec with per-request pinned snapshots. Root ownership is explicit, error records are bounded with private causes, and Strict Mode does not own host-store destruction. React 19.3.1/jsdom qualification is DOM emulation, not live-browser or all-version certification; streaming/RSC/framework auto-hydration are unavailable. See its [README](packages/@zeruxjs/react/README.md).
- `@zeruxjs/vue` retains standalone non-Vue refs and injected scope bindings; optional `/browser`, `/server` and `/rendering` entries own native runtime-only Vue apps, updates, hydration and fresh-app SSR. Matching 3.5.44+ peers within 3.5 are required; the exported compiler-free server build rejects request-time templates. No SFC compiler integration is added. Per-app context owns cancellation/disposers, SSR uses one-shot store reads, and teleports/streaming/framework auto-hydration remain unavailable. Controlled input hydration follows Vue model replacement; native watchers stop on unmount, while retained detached-node event callbacks need host signal guards. Vue/jsdom qualification is DOM emulation; see its [README](packages/@zeruxjs/vue/README.md).
- `@zeruxjs/db` manages connector lifecycles, capability metadata, bounded pending/batch execution, redacted metric hooks and validated keyset continuations; SQL connectors share `db-sql-core`. Cancelled callers retain slots until driver settlement; cancellation does not prove rollback. PostgreSQL native-compatible pools expose pinned async transactions and destructive cancellation. MySQL pools expose pinned async DML transactions with cooperative deadlines, explicit FOUND_ROWS policy and string-preserving precision; MySQL native cancellation/transactional DDL and query-only pinned injection remain unsupported. MongoDB explicitly enabled client-backed transactions probe replica-set/mongos session support, pin CRUD/aggregation sessions and never replay callbacks; optional commit-only retries are bounded. ## Engineering and security boundaries

- Validate untrusted input at each boundary, including runtime inputs from JavaScript/JSON. Bound body sizes, collection sizes, concurrency, execution time and retries; propagate cancellation where supported.
- Enforce authentication and authorization server-side for each operation and tenant. Never trust client role/tenant claims or forwarded headers without explicit verification and trusted-proxy configuration.
- Use parameterized SQL and validated identifiers. Prevent path traversal and symlink escape in filesystem operations; avoid interpolating untrusted values into shell commands.
- Apply origin/CSRF protections to cookie-authenticated writes. Escape output for its destination context and keep credentials out of browser bundles, public configuration and error responses.
- Restrict outbound destinations and redirects where URLs are configurable. Account for SSRF and DNS rebinding; URL syntax validation alone is not an egress policy.
- Make resource ownership, deadlines and cleanup explicit. Avoid cross-request mutable globals, unbounded caches, blocking work in request handlers and duplicate background workers.
- Use atomic operations or real transactions for competing writes. Do not label in-memory locks as distributed coordination, operation arrays as transactions, or at-least-once jobs as exactly-once delivery.
- Keep errors actionable without exposing tokens, private payloads or internal stack traces to clients. Preserve error causes internally and do not silently swallow failures that affect correctness.
- Preserve public API compatibility unless a breaking change is authorized. Document changed behavior, migration requirements and operational limits alongside the implementation.
- Reuse existing dependencies and repository utilities. Add dependencies only when necessary; review runtime compatibility, license, maintenance, install scripts and bundle impact. Use npm to update lockfiles; never invent integrity hashes or external resolutions.
- Measure before claiming a performance improvement. Explain workload and tradeoffs, and distinguish a local benchmark from production behavior.
